# 余声核心对话闭环设计

> 日期：2026-07-14
> 状态：各设计段和书面版本均已由用户确认
> 范围：人物事实、关系记忆、表达风格、对话生成、失败降级、效果评价
> 不包含：视觉重构、商业化、社交广场和无关功能扩张

## 1. 一句话结论

余声是一款经授权的声音记忆陪伴产品：它根据真实声音、已确认的人物资料和关系记忆，生成听起来像、表达习惯像、有情绪的语音回应，但不冒充本人，也不把模型生成内容说成本人的真实想法、承诺或遗愿。

产品同时覆盖声音主人健在和已经离世两类场景。两类场景共用人物与对话模型，但授权、审核和效果数据必须分开处理。

## 2. 已确认的产品决策

1. **事实受约束，表达可以像本人。**事实必须有依据；称呼、口头禅、句式和情绪可以贴近本人；生成观点不得冒充本人真实意志。
2. **健在与逝者场景同时验证。**两组结果分别统计，不能用合并平均数掩盖某一组失败。
3. **北极星指标是有效还原会话率。**页面访问量、构建成功和对话次数都不能替代真实还原评价。
4. **人物资料分三层。**人物事实、关系记忆和表达风格分别存储、检索和使用。
5. **分风险、单次流式生成。**不增加第二次生成模型调用；先做边界判断和证据检索，再用一次流式调用生成可直接朗读的短句。
6. **AI 只提取候选。**候选资料必须由用户逐条确认后，才能进入真实对话。
7. **失败时安全降级。**宁可少说，也不允许模型脱离可靠资料继续编造；未达到真实验收门槛不得更新 Production。

## 3. 产品目标与范围

### 3.1 目标用户

- 希望保存自己或健在亲友声音，并进行长期家庭陪伴的用户。
- 希望在私密范围内保存逝者声音与共同记忆的家庭成员。
- 参与评价的人必须认识声音主人，能够判断声音、表达和情绪是否贴近本人。

当前没有用户访谈证据，所以“用户是否愿意持续使用”仍是假设。本阶段先证明核心还原价值，不用功能数量替代用户验证。

### 3.2 本阶段要做

- 将自由文本人物描述升级为可追溯、可确认、可撤回的三层人物资料。
- 让 AI 从用户材料中提取候选资料，但不自动写入真实档案。
- 对话只引用已确认内容，并记录本轮使用过的证据。
- 在检索失败、资料冲突、模型失败和语音失败时安全降级。
- 建立会话评分和延迟指标，能够计算有效还原会话率。
- 用健在组和逝者组分别做真实有声会话验收。

### 3.3 明确不做

- 不做视觉风格、布局和设计系统重构。
- 不做“复活”、通灵或代替本人表达真实意志的产品叙事。
- 不让模型生成内容自动成为人物事实或记忆。
- 不在 0→1 阶段建设完整人生知识图谱、复杂家庭关系图或多智能体系统。
- 不用虚构数据、单元测试或页面 HTTP 200 证明产品已经可用。

## 4. 成功指标

### 4.1 北极星指标

北极星指标为**有效还原会话率**：满足全部条件的评分会话数，占全部有效评分会话数的比例。

一次有效评分会话必须完成至少三轮有声对话，并由认识声音主人的用户提交完整评分。一次会话只有同时满足以下条件才算成功：

- 声音相似度至少 4/5；
- 表达习惯相似度至少 4/5；
- 情绪合适度至少 4/5；
- 事实可信度至少 4/5；
- 不适感不高于 2/5；
- 没有重大事实编造、身份冒充或授权越界。

### 4.2 0→1 验证门槛

- 健在组：至少 10 位用户、30 次有效评分会话，有效还原会话率至少 60%。
- 逝者组：至少 10 位用户、30 次有效评分会话，有效还原会话率至少 60%。
- 两组分别达标才算核心价值初步成立。
- 连续 20 轮真实有声对话中，至少 80% 在用户输入结束后 4 秒内开始播放第一句声音。

留存率和对话完成率作为辅助指标，不作为当前北极星指标，因为它们不能直接证明“像本人”。

## 5. 三层人物资料

### 5.1 人物事实

描述相对稳定、可核实的信息，例如姓名、关系、家庭成员、重要经历、长期偏好和明确立场。每条事实必须包含：

- 归属人物；
- 事实类别和正文；
- 至少一个有效来源；
- 创建者与确认者；
- 状态：`pending`、`confirmed`、`rejected`、`conflicted` 或 `revoked`；
- 确认时间；
- 可选的发生时间与失效时间。

只有 `confirmed` 状态可以进入对话上下文。

### 5.2 关系记忆

描述用户与声音主人的共同经历，例如“2008 年暑假教我做葱油饼”。每条记忆除通用状态和来源外，还可以记录发生时间、地点、参与人和原始描述。

关系记忆需要向量化以支持语义检索，但向量相似不代表事实成立。检索前必须先按用户归属、人物和 `confirmed` 状态过滤。

### 5.3 表达风格

描述“怎么说”，不描述“发生过什么”，包括：

- 对用户的称呼；
- 常用口头禅；
- 句子长短和节奏；
- 安慰、提醒、拒绝和表达关心的方式；
- 常见情绪、强度、语速和停顿；
- 来自真实材料的短句示例。

表达风格可以影响措辞和语音控制，但不能生成新事实。风格项同样需要来源和确认状态。

### 5.4 来源与候选项

系统记录资料来源，例如用户手写、聊天记录、音频转写或其他文字材料。AI 从来源中提取候选事实、关系记忆和表达风格，候选默认是 `pending`。

用户必须逐条确认、修改或拒绝。确认后才生成检索向量并进入对话。相同人物、相同事实类别和相同事实键出现不兼容值时，系统将相关候选放入同一冲突组；AI 可以提示其他疑似冲突，但不能替用户决定哪个是真的。冲突解决前相关内容全部排除。模型回复和聊天临时信息永远不能自动成为已确认资料。

## 6. 建议的数据边界

实现时使用以下数据边界，不得把三层语义重新合并成一段自由文本：

- `persona_sources`：原始材料的类型、私有对象引用、校验和、创建者和处理状态。
- `persona_facts`：人物事实及确认状态。
- `relationship_memories`：共同经历、参与人、时间、向量和确认状态。
- `speech_style_items`：称呼、口头禅、句式、情绪习惯和示例。
- `persona_item_sources`：事实、记忆或风格项与一个或多个来源之间的关联。
- `message_evidence`：一条助手消息使用过的资料类型和资料 ID。
- `conversation_sessions`：一次连续会话、场景分组和核心耗时。
- `conversation_feedback`：五项评分、红线问题和评价人。

所有资源继续通过已验证的人物归属间接绑定 `userId`。SQLite 本地适配器和 Postgres 生产适配器必须保持相同语义，Production 不允许回退到本地存储。

## 7. 资料录入流程

1. 用户提交文字、聊天记录或音频转写材料。
2. 系统保存私有来源和校验和，不把原文写入日志。
3. AI 提取结构化候选项，并标明候选类型和来源片段。
4. 候选项以 `pending` 保存，不能被对话检索。
5. 用户逐条确认、修改或拒绝。
6. 系统检查与已有资料是否冲突；冲突项暂停使用。
7. 确认后的事实和记忆生成检索数据，风格项进入人物风格集合。
8. 撤回或删除来源时，系统重新判断依赖该来源的已确认项；没有其他有效来源的内容停止使用。

只允许增加完成该流程所需的功能入口，不进行视觉重设计。

## 8. 对话生成流程

每轮对话按以下顺序处理：

1. 校验登录、人物归属、声音授权和请求大小。
2. 将用户消息持久化；持久化失败时不开始生成。
3. 处理确定性边界：自伤危险、身份真实性、复活、遗愿、承诺和授权撤回等问题不交给模型自由发挥。
4. 只从 `confirmed` 人物事实和关系记忆中检索证据，并单独加载已确认表达风格。
5. 判断本轮模式：
   - `grounded`：有可靠证据，可以引用已确认事实或记忆；
   - `companionship`：没有相关证据，只能倾听、安慰或邀请用户补充；
   - `boundary`：命中身份、安全或真实意志边界，使用固定或受限回应。
6. 用明确分区的上下文进行一次流式模型调用。事实、记忆、风格和临时聊天历史不能混成一段无标记文本。
7. 模型只输出可直接说出口的短句；第一完整句立即进入 TTS，不等待整段结束。
8. 保存最终回复、本轮模式、证据 ID、首句时间、TTS 时间和降级原因。
9. 本轮出现的新信息只属于临时聊天历史；用户主动确认后，才可走候选资料流程。

为了控制首句延迟，本阶段不增加“先让一个模型规划、再让另一个模型生成”的双调用链路。硬边界使用确定性规则，事实可靠性依靠确认状态、检索过滤、上下文分区和固定反例测试共同保证。

## 9. 失败与安全降级

| 失败情况 | 处理方式 |
| --- | --- |
| 资料提取失败 | 保留原始材料，整批候选不写成可用资料，允许重试 |
| 资料互相矛盾 | 标记为 `conflicted`，相关内容全部停止用于对话，等待用户解决 |
| 嵌入或记忆检索失败 | 切换到 `companionship`，不得引用人物事实，并记录降级原因 |
| 模型生成失败 | 保留用户消息，不伪造成功回复，允许重试 |
| 助手消息保存失败 | 本轮不标记成功，不计入有效会话 |
| TTS 失败 | 保留文字，只重试当前句，不切换人物声音 |
| 声音授权撤回 | 立即禁止新的预置音色、TTS 和人物化有声回复 |
| 身份、复活或真实意志问题 | 使用明确 AI 披露，不允许模型冒充本人回答 |
| 自伤或现实危险 | 停止人物化表达，优先现实支持和专业帮助 |

降级不等于静默吞错。用户能得到可理解的功能反馈，服务端记录不含原始声音、密码、密钥和完整私密资料的结构化原因。

## 10. 测试与真实验收

### 10.1 自动化测试

- 数据模型与迁移：状态约束、来源关系、冲突状态、撤回和幂等迁移。
- 数据隔离：两个用户不能读取、确认、检索或删除对方的人物资料。
- 候选确认：`pending`、`rejected`、`conflicted` 和 `revoked` 内容永远不能进入对话证据。
- 检索：只返回当前人物的已确认事实与记忆，检索失败必须进入 `companionship`。
- 提示词与边界：事实、记忆和风格明确分区；身份、遗愿、承诺和未知事实有固定反例。
- 消息证据：每条 `grounded` 回复能追查使用过的资料 ID。
- 延迟与流式：第一完整句及时发出，TTS 失败只影响当前句。
- 评分：会话必须满足三轮和完整评分条件，成功判定按五项评分与红线共同计算。

### 10.2 固定行为探针

使用虚构人物和固定资料，持续覆盖：

- 已知事实；
- 与事实冲突的问题；
- 诱导共同经历；
- 未知遗愿和承诺；
- 代替用户做重大决定；
- 身份、复活和另一个世界；
- 仅在当前聊天出现、尚未确认的信息；
- 检索失败与资料冲突。

重大事实编造和身份冒充必须为 0。固定探针只能证明技术行为，不能替代真实用户评分。

### 10.3 Preview 与用户验收

进入 Production 前必须同时证明：

1. 真实 Neon、Private Blob 和声音供应商均可用，重新部署后资料仍可读回。
2. 两个测试账户之间人物、资料、声音和消息完全隔离。
3. 授权撤回后新对话和 TTS 立即停止，删除状态可追踪。
4. 健在组和逝者组分别达到第 4.2 节的样本数与有效还原会话率。
5. 连续 20 轮真实有声对话的首句播放速度达到目标。
6. Preview 没有阻断性 5xx、空白回复或未记录的静默降级。

## 11. 实施顺序

1. 增加三层资料、来源、候选、证据和反馈的数据模型，并完成 SQLite/Postgres 一致性测试。
2. 增加候选提取、确认、拒绝、冲突和撤回的服务边界与 API。
3. 将现有自由文本记忆兼容迁移为有来源的已确认关系记忆，不删除旧回退数据，迁移结果必须可审计。
4. 重构对话检索和提示词分区，加入模式判断、证据记录和安全降级。
5. 增加最小功能性确认入口与会话评分入口，不做视觉改版。
6. 完成自动测试、固定行为探针和本地真实模型复测。
7. Neon 条款解锁后，在独立 Preview 数据库执行迁移、双账户隔离、重部署读回和真实有声验收。
8. 两组有效还原会话率和上线硬门槛全部达标后，再单独决定是否更新 Production。

## 12. 当前已知风险

- 尚未进行用户访谈，用户是否愿意录入足够材料和持续使用仍未证明。
- 逝者场景无法由声音主人本人评价，需要由熟悉其声音和表达的人评分，结果可能受回忆偏差影响，所以必须与健在组分开。
- 当前 SiliconFlow 真实模型探针的首句延迟 P95 为 4.083 秒，4 秒目标尚未稳定达成。
- 当前 Preview 缺少 Neon 数据库配置，登录接口会返回 500；数据库解锁前不能完成线上闭环验证。
- 供应商用户预置音色仍受账号实名认证影响，尚无真实成功证据。
- 有效还原会话率 60% 是 0→1 初始门槛，不代表产品已经成熟；达到后仍要根据分项得分和失败样本继续提升。

## 13. 完成定义

本阶段不是以代码合并或构建成功结束。只有以下事实全部成立，才能认为核心对话闭环完成：

- 三层人物资料已经替代自由文本直接驱动模型；
- 未确认、冲突、拒绝和撤回内容无法进入对话；
- 每条有事实依据的回复可以追查证据；
- 检索和供应商失败会安全降级，不会自由编造或切错声音；
- 有效还原会话率可以从真实用户评分中计算；
- 健在组和逝者组分别达到初始成功门槛；
- 首句速度、真实存储、用户隔离、授权撤回和重新部署读回全部通过 Preview 验收；
- Production 更新经过单独确认，且上线后没有阻断性错误。
